# Ghostlink for Windows

These notes include unmerged changes in the local `codex/tauri-windows-prototype` worktree. They are saved on `main` for continuity; the application source and test scripts on `main` do not yet include all of this work. The next task is described in the [fullscreen helper handoff](fullscreen-helper-handoff.md). Electron no longer needs to be maintained as a runnable reference; its historical notes below describe the migration only.

Ghostlink 0.8 uses Tauri 2, Rust and WebView2 on Windows. It shares its control panel with the Electron reference app. The overlay shows guest pointers and the private test pointer.

Open `src-tauri/target/x86_64-pc-windows-msvc/release/ghostlink-tauri-prototype.exe` to try the local build without installing. Run `npm ci` once and `npm run prototype:dev` to run from source. `npm run prototype:build` creates the local Windows x64 installer under `src-tauri/target/x86_64-pc-windows-msvc/release/bundle/nsis/`. Tauri uses a separate app identifier from Electron. The installer uses the existing WebView2 Evergreen Runtime if available, or downloads Microsoft's bootstrapper if the runtime is missing.

1. Ghostlink starts with the primary display or your last saved area. Click **Full Screen** to use the whole display, or **Drag frame** to draw a rectangle. Press Esc in the picker to keep the previous frame.
2. On Windows, click **Pick window** and point at another app before the countdown ends. An asterisk follows your pointer while the picker is active. The selection follows the window as it moves or resizes. Minimizing or closing the window suspends its shared area; restoring a minimized window resumes it. **Frame on/off**, beside **Shared display**, hides only the border and is remembered between launches.
3. After connecting, your guest’s arrow disappears when they leave their shared area. Click through a guest arrow to interact with the app underneath.
4. Click the bug button to open the private trackpad. Move inside the pad to place the blue **Test user** pointer in the shared area. Click the trackpad to see it blink. **Relays** checks signaling reachability, and **Test peer** checks a separate WebRTC connection to the main panel using a fresh random secret. The pointer preview works locally while these checks run. Close the trackpad or press Esc to end the test.
5. On a two-display setup, give the displays different scales and repeat on both. Move the secondary display to the left of and above the primary to test negative X and Y. Restart the prototype after changing display settings so it refreshes the display list.

To connect to a friend, select your shared area first, then enter a username and the same secret in both apps. Click **Connect** in both. Movement maps between your two areas, and a left click inside your area on Windows makes your arrow blink for the other person. Opening the private trackpad pauses sending your desktop pointer until you close it. Signaling uses the same public relays as the Electron app.

Run `cargo test --locked --manifest-path src-tauri/Cargo.toml` for the coordinate tests. They cover negative origins and edge inclusion, but cannot prove how Windows and WebView2 behave on a physical multi-display layout.

The area logic, React panel, and drag picker share the same code on Windows and Linux. Linux X11 has a fallback through Tauri for window placement and cursor position that still needs desktop testing. The panel disables desktop areas under Wayland and offers Pick window on Windows only.

## Migration notes

Electron 0.7.0 polls the cursor every 33 ms, calibrating Electron's cursor coordinates against a Win32 helper. It stores the play area in physical pixels, normalizes and quantizes movement for the peer, and captures click pings with `uiohook-napi`. Full Screen uses the selected monitor bounds. Drag frame maps a drag on the display screenshot or interactive overlay to the display rectangle. Pick window uses the native window bounds under the pointer. The desktop-wide Electron overlay projects incoming coordinates into the local play area, calibrates its CSS space against the desktop bounds, and ignores clicks except during interactive selection.

The platform layer reads the pointer in physical pixels. On Windows it also captures left clicks during a sharing session, queries the window under the pointer, and shows the overlay without activating it. The overlay checks its client bounds before showing and maps normalized positions into its viewport. React reuses `CursorMark`, its blink animation, and Electron’s Trystero room and message code. The private trackpad sends movement and clicks through local Tauri commands. Sending desktop click pings is currently Windows-only.

## Magpie scaling

Windows Pick window now tracks a window handle instead of saving a one-time rectangle. While Magpie is scaling that window, Ghostlink samples the real mouse in Magpie's source rectangle and draws guests in its destination rectangle. The destination excludes letterbox bars. These rectangles and the source handle are read from Magpie's window properties; no Magpie code is included in Ghostlink. This integration was checked against Magpie 0.13.0 and depends on its current window metadata.

To try it, run the local Ghostlink executable, put the game in windowed mode, and use Pick window. Start Magpie windowed or fullscreen scaling, or select the game after starting scaling. Moving, resizing, entering fullscreen, and exiting scaling should update the overlay without another selection. Use Frame off to remove the green border while keeping guests visible. Magpie remains responsible for entering/exiting scaling and its shortcuts in this build.

Local desktop checks on November 11, 2026 used a 1920 × 1200 display at 125% scaling and an Explorer window: picking before scaling, maximizing/restoring, windowed scaling, switching to fullscreen scaling, picking after scaling, and exiting scaling all kept the overlay in the displayed image. A synthetic guest remained visible over fullscreen scaling with the frame off. The code tests also cover signed negative monitor coordinates and updated source/destination bounds. After automation stopped, the user confirmed the mouse could reach all four edges of the visible fullscreen image, resolving a possible leftward-confinement concern during the shared-control test. The fullscreen image had 80-pixel side margins, and Magpie intentionally confines the mouse to the image while the source is focused. Ghostlink does not move or confine the system cursor. The user subsequently confirmed a successful two-PC fullscreen game test with Magpie. Detailed guest-pointer edge alignment and game-specific Alt-Tab/camera-lock behavior still need targeted trials. Mixed physical display scaling remains skipped as requested.

Minimizing the selected window clears the current input/display mapping and hides the overlay. The native peer session and React room membership remain active. If the last shared pointer was visible, the sampler sends a null-position update to hide it on peers; unchanged null samples are not repeatedly sent. Desktop movement/clicks are not shared while the target is minimized. Incoming peer data and normal WebRTC/signaling maintenance can continue. Restoring the same window restores its mapping and resumes sharing without rejoining the room, assuming the network connection remains healthy.

An integrated “select window → present fullscreen → exit with hotkey” mode is feasible using a dedicated native presentation helper. Upstream Magpie exposes `ScalingRuntime::Start(HWND, ...)` / `Stop()` internally in a C++ static library, but does not provide a ready-made external command to scale an arbitrary window handle. A controlled helper or a separate Rust capture/presentation implementation would be needed for that workflow. Keep this Windows implementation behind the platform boundary; the shared React UI and peer protocol do not need to change. Native exclusive-fullscreen games remain a separate rendering-hook problem.

Magpie 0.13.0 documents its scaling-state notifications, stable window class, source/destination bounds, and overlay ordering. It provides its core as a C++ static library rather than an external start-by-window-handle command. A first integration prototype should wrap the pinned core in a Windows-only helper with start/stop/status control and basic fit-to-monitor scaling. The existing React panel, peer protocol, Rust window tracking, and guest overlay can remain in place. Measure latency, GPU usage, installer size, and exit/crash cleanup before expanding it.

Magpie is GPLv3; its application source notice allows version 3 or later. Ghostlink adopts the same `GPL-3.0-or-later` terms in the root LICENSE. Matching package metadata changes are present in the unmerged local worktree. Third-party notices and licenses must remain intact. Copying or linking Magpie code requires GPL-compliant distribution of the resulting combined work, including the relevant notices and corresponding source/build instructions. A separately distributed helper still has its own GPL obligations, and a process boundary alone does not establish that a tightly coupled application is a separate work.

Both a separate Magpie fork and a source snapshot inside Ghostlink can comply with the license. The source layout does not change the distribution obligations. The recommended next prototype uses a pinned source snapshot under `third_party/magpie/` and a small Windows helper under `native/fullscreen-host/`, built and packaged with Tauri. Record the upstream tag/commit, retain upstream LICENSE/notices, and document changes and build inputs. Keep the core as a separate process so capture/presentation failures can be isolated from the panel and peer session. These directories have not been added yet. A future matching source archive must include the actual modified core and helper, not just a link to upstream's latest branch. If a git submodule is used instead, GitHub's automatic source archive will not by itself include its contents.

Upstream references: [documented programmatic cooperation](https://github.com/Blinue/Magpie/blob/v0.13.0/docs/Interact%20with%20Magpie%20programally.md), [runtime entry points](https://github.com/Blinue/Magpie/blob/v0.13.0/src/Magpie.Core/include/ScalingRuntime.h), [capture methods](https://github.com/Blinue/Magpie/blob/v0.13.0/docs/Comparison%20of%20capture%20methods.md), [Magpie license](https://github.com/Blinue/Magpie/blob/v0.13.0/LICENSE), and [GNU guidance on linking and separate programs](https://www.gnu.org/licenses/gpl-faq.en.html#GPLStaticVsDynamic).

## Fullscreen Overlay Clock investigation

Reviewed TheConfax/Fullscreen-Overlay-Clock at commit `f1897c40411a3b28e9831ac334636a7027a94639` on November 12, 2026. Its project code is MIT-licensed. Relevant code can be adapted with the required copyright/permission notice retained, without adding its Python/PyQt runtime to Ghostlink.

Its README explicitly excludes exclusive fullscreen games. `src/services/win32.py:is_fullscreen_app` detects borderless windows covering a monitor and excludes windows outside the desktop Z-order band. `reassert_topmost` calls SetWindowPos(HWND_TOPMOST) without activation; click-through uses WS_EX_LAYERED / WS_EX_TRANSPARENT, and foreground changes use SetWinEventHook. `src/ui/clock.py` also reasserts topmost on a 500 ms timer. It has no game-rendering hook or native-exclusive-fullscreen backend. These techniques could improve ordinary overlay focus/visibility handling, but do not provide the missing exclusive-fullscreen support. This finding is based on source inspection; the clock application was not installed or runtime-tested.

Sources: [README limitations](https://github.com/TheConfax/Fullscreen-Overlay-Clock/blob/f1897c40411a3b28e9831ac334636a7027a94639/README.md#limitations), [Win32 implementation](https://github.com/TheConfax/Fullscreen-Overlay-Clock/blob/f1897c40411a3b28e9831ac334636a7027a94639/src/services/win32.py#L919-L956), and [MIT license](https://github.com/TheConfax/Fullscreen-Overlay-Clock/blob/f1897c40411a3b28e9831ac334636a7027a94639/LICENSE). No code from this project has been copied into Ghostlink.

## Signed updates

Release builds check for availability after launch. Click the update icon once to check again, download, verify, install, and restart. The Windows installer runs quietly during an update. A local build without a feed keeps the update icon dimmed.

Generate a persistent updater key with `npm exec -- tauri signer generate -w <private-key-path>`. Keep a backup of the private key and password outside the checkout. Set these GitHub Actions values before running the Release workflow.

- Repository variable `TAURI_UPDATER_PUBLIC_KEY` holds the contents of the generated public key file.
- Repository secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` hold the private key file contents and password. Keep the same signing key for later updates to this release channel.
- To Authenticode-sign the Windows installer and executable, configure the signing provider on the runner and set the repository variable `TAURI_WINDOWS_SIGN_COMMAND` to its Tauri signing command. The command must include Tauri's `%1` file placeholder and timestamp the signature. The release script verifies both signatures and timestamps when the command is supplied.

The workflow uploads the NSIS installer, its Tauri `.sig`, and `latest.json` to a draft GitHub Release. `latest.json` contains the version, the versioned installer URL, and the updater signature. The app reads the stable `releases/latest/download/latest.json` URL from the same public repository. Publish the draft as the latest release after reviewing all three assets. Publish future releases the same way so installed copies can find them.

To build the same assets locally from the repo root, set the same environment variables and run `./scripts/build-tauri-release.ps1 -Repository paavalipopov/ghostlink -Tag v0.8.0` in PowerShell 7. The script writes the release assets under `dist/release`. Build-time Authenticode signing runs before Tauri generates the updater signature.
